# 02 关键数据结构

> 本篇逐个拆解项目里的核心数据结构：它们长什么样、解决什么问题、边界在哪里。

## 0. 结构总览

| 结构 | 用途 | 线程安全 | 阻塞语义 |
| --- | --- | --- | --- |
| `PacketQueue` | 解封装线程 → 解码线程 | 是 | push/pop 都阻塞 |
| `FrameQueue` | 解码线程 → 渲染/音频消费 | 是 | push 阻塞、pop 不阻塞 |
| `RingBuffer<T>` | 音频解码线程 → WASAPI 回调 | 是 | 非阻塞（满了丢/等下次） |
| `PlaybackClock` | 全局播放时钟 | 是 | 无 |

## 1. PacketQueue（包队列）

### 作用

解封装线程产出 `AVPacket`（压缩数据 + 时间戳），解码线程按需消费。队列是两者之间唯一的联系。

### 结构

```cpp
class PacketQueue {
    std::mutex              mutex_;
    std::condition_variable cv_;
    std::deque<AVPacketUPtr> queue_;   // unique_ptr 管理 AVPacket 生命周期
    size_t max_packets_ = 0;            // 按个数限流
    size_t max_bytes_   = 0;            // 按字节限流（更准确）
    size_t bytes_       = 0;
    bool   aborted_     = false;
};
```

### 解决什么问题

- **速率不匹配**：生产快、消费慢，队列缓冲；
- **突发吸收**：解码慢的瞬间，队列里的包让解码线程不至于饿死；
- **背压**：队列满时 push 阻塞，把压力传导回解封装线程，限速生产；
- **生命周期**：`unique_ptr` 让 AVPacket 的释放（`av_packet_free`）不可能被忘记。

### 关键伪代码

```cpp
void push(AVPacketUPtr pkt) {
    unique_lock lk(mutex_);
    cv_.wait(lk, [&]{ return aborted_ || bytes_ < max_bytes_; });  // 满则等
    bytes_ += pkt->size;
    queue_.push_back(std::move(pkt));
    cv_.notify_one();               // 唤醒一个消费者
}

AVPacketUPtr pop() {
    unique_lock lk(mutex_);
    cv_.wait(lk, [&]{ return aborted_ || !queue_.empty(); });
    if (aborted_ && queue_.empty()) return nullptr;   // 终止信号
    auto pkt = std::move(queue_.front());
    queue_.pop_front();
    bytes_ -= pkt->size;
    return pkt;
}
```

### 边界条件

- **满队列 + abort**：等待条件 `aborted_` 成立，pop 返回 nullptr，push 也立即返回——退出不卡死。
- **abort 后 reset**：abort 是"一次性终止"，重开文件（同一 MediaPlayer 复用队列）必须先 `reset()` 清除终止态，否则新解码线程一启动就退出（docs/06 坑 AD）。
- **flush 清空**：flush 时也要 notify_all，否则正在 wait 的消费者醒不过来。
- **字节统计**：`pkt->size` 是压缩包大小，用它限流比个数限流更贴合真实内存占用（一个 GOP 的 I 帧包可能顶几十个 P 帧包）。

## 2. FrameQueue（帧队列）

### 作用

解码线程产出 `AVFrame`（解码后的 YUV 数据 + pts），本项目只设一条**视频**帧队列；音频解码后经重采样直接写环形缓冲（见第 3 节），少一跳拷贝。

### 与 PacketQueue 的三个关键区别

1. **pop 不阻塞**：渲染线程用"有帧就画，没帧就等一小会"的方式轮询，避免被队列卡住无法响应 seek/暂停。
2. **上限很小**：视频帧通常 3–8 帧（1080p 一帧 YUV420 约 3MB）。
3. **需要按 pts 排序**（视频）：部分封装/解码顺序下帧可能乱序，队列维护"最后出队 pts"用于丢帧判断。

### 为什么帧队列上限必须小

帧已经解码完成，占的是**显存/内存大头**（NV12 1080p 每帧 3MB，60fps 一秒 180MB）。包队列里是压缩数据（小），帧队列里是解压数据（大），**越靠后环节缓冲越小**，这条原则贯穿整个管线。

## 3. RingBuffer<T>（环形缓冲）

### 作用

承载 WASAPI 回调与音频解码线程之间的 PCM 数据流（float32 交错采样）。

### 结构

```cpp
template <typename T>
class RingBuffer {
    std::vector<T> data_;     // 固定容量
    size_t head_ = 0;         // 读位置
    size_t tail_ = 0;         // 写位置
    size_t count_ = 0;        // 当前元素数
    std::mutex mutex_;
};
```

用 `count_` 而不是"head==tail 表示空"的经典歧义：

- `head == tail && count == 0` → 空；
- `head == tail && count == capacity` → 满。

### 为什么回调线程要"非阻塞"

WASAPI 音频回调是**系统硬实时线程**，在里面加锁等待会造成爆音甚至死锁。因此：

- 音频解码线程**写**：`push()` 满时丢弃最旧数据或等待下一次；绝不阻塞系统回调；
- 回调线程**读**：`pop()` 只做"有就取，没有就写静音"，单次加锁开销极小。

## 4. PlaybackClock（播放时钟）

### 作用

全局唯一"现在播放到第几秒"，支撑同步、进度条、seek。

### 结构

```cpp
class PlaybackClock {
    double base_pos_  = 0;    // 基准位置
    int64  base_qpc_  = 0;    // 基准时刻（QueryPerformanceCounter）
    double rate_      = 1.0;  // 变速倍率
    bool   paused_    = false;
    std::mutex mutex_;

    double now() const;       // QPC 换算秒数
    double get() const;       // base_pos_ + (now() - base_qpc_) * rate_
    void   set_pos(double p); // seek：base_pos_=p, base_qpc_=now()
    void   set_rate(double r);
    void   set_paused(bool p);
};
```

### 为什么用 QPC 而不是 std::chrono::steady_clock

Windows 上 QPC 是精度最高的单调计时器（微秒级），且不被系统时间调整影响。`steady_clock` 通常也够用，但 QPC 是 Windows 多媒体程序的惯例，顺带学一个原生 API。

### 边界条件

- **变速**：只改 `rate_`，不挪 `base_`，位置曲线自然变陡/变缓；
- **暂停**：暂停瞬间把位置"冻结"到当前值（记入 base_pos_），恢复时更新 base_qpc_；
- **seek**：`set_pos` 后所有线程读到的新位置立即跳变，解码器/队列必须同步 flush（见 03 篇）。

## 5. 各结构解决的问题对照表

| 症状（不解决会怎样） | 对应结构 | 机制 |
| --- | --- | --- |
| 解码慢一点画面就卡 | PacketQueue | 缓冲 + 背压 |
| 内存被解压帧吃光 | FrameQueue 小上限 | 帧数限流 |
| 爆音/丢失节拍 | RingBuffer 非阻塞 | 宁可静音不可阻塞 |
| 快进快退后时间错乱 | PlaybackClock | 基准点 + 倍率 |
| 退出时线程卡死 | abort + notify_all | 协议保证 |
