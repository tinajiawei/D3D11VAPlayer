# 03 时间戳与音视频同步

> 播放器最容易"玄学"的部分。本篇把 pts/dts/time_base 讲透，然后给出音频主时钟的完整算法。

## 1. 时间戳体系：pts / dts / time_base

### 概念

- **DTS（Decode Time Stamp）**：这一帧**应该被解码**的时间。
- **PTS（Presentation Time Stamp）**：这一帧**应该被显示**的时间。
- **time_base**：时间戳的单位。`pts * time_base = 秒`。

### 为什么有 DTS 和 PTS 两个？

编码器为了压缩率引入 **B 帧（双向参考帧）**：解码 B 帧之前必须先解码后面的帧。于是：

- 包在文件里的顺序 = DTS 顺序（解码顺序）；
- 帧显示的顺序 = PTS 顺序（播放顺序）。

没有 B 帧的码流（如多数低延迟配置）两者一致；有 B 帧时，解码线程必须**按 PTS 重排输出**，这正是帧队列排序职责的来源。

### 换算公式（必须写对）

```cpp
// 流的时间基，来自 AVStream::time_base
double time_base_sec = av_q2d(stream->time_base);

// 帧显示时刻（秒）
double pts_sec = frame->pts * time_base_sec;

// 时长（秒）
double duration_sec = stream->duration * time_base_sec;
```

常见坑：

- `frame->pts` 是 `AV_NOPTS_VALUE`（缺时间戳）时必须用上一帧 + 平均帧长补齐，否则同步直接崩溃；
- 不要把 `stream->time_base` 和 `AV_TIME_BASE`（1e6）混用；
- seek 时时间单位换算同样要乘 time_base。

## 2. 音频主时钟（Audio Master Clock）

### 为什么音频当"老板"

人耳对音频抖动极敏感（10ms 级别的断续都能察觉），人眼对视频抖动宽容得多（几十 ms 无感）。所以让**音频按自己的真实节奏走**，视频去**追**音频，这是 ffplay 也是本项目的选择。

### 音频时钟怎么来

不靠"解码线程输出了多少数据"推算，而是直接问音频硬件：

```cpp
// WASAPI IAudioClock 直接给出已播放位置（100ns 单位）
UINT64 pos = 0, qpc = 0;
audio_clock->GetPosition(&pos, &qpc);
double played_seconds = pos / 10000000.0;
```

这个位置来自声卡自己的采样计数器，**不含缓冲区预读部分**，精确且天然平滑。

> 实测本机部分虚拟音频驱动的 `IAudioClock` 位置推进异常（6 秒只走 0.2 秒），所以项目保留"帧计数时钟"做交叉校验：计数 = 已写入声卡的帧数 − 设备缓冲水位（`GetCurrentPadding`），即**声卡真正消费的位置**。直接数"已写帧数"会一直领先可听声音约一个设备缓冲（最多 0.2s），画面会稳定快于声音——这是本项目真实踩过的坑（docs/06 坑 Z）。

### 全局主时钟

```cpp
double SyncEngine::master_clock() {
    if (有音频流 && 音频正常) return audio_clock_秒;   // 硬件时钟
    return playback_clock_.get();                        // 无音频时 QPC 回退
}
```

## 3. 视频追音频：延迟算法

渲染线程每拿到一帧视频，算它"应该出现在哪个时刻"，再与主时钟比较：

```cpp
// frame_pts：这一帧该显示的时刻（秒）
double diff = frame_pts - master_clock();

// 帧太早（视频超前）：睡到该显示的时刻
if (diff > SYNC_MAX_DELAY) diff = SYNC_MAX_DELAY;   // 防跳变
if (diff > 0) sleep(diff);

// 帧太晚（视频落后）：直接丢弃，追上音频
if (diff < -SYNC_DROP_THRESHOLD) 丢弃本帧;
```

### 阈值为什么不能拍脑袋定

- 丢弃阈值太小（如 -5ms）：网络/解码正常波动都会丢帧，画面糊；
- 丢弃阈值太大（如 -200ms）：画面长时间落后，观感割裂。

本项目取：

```cpp
constexpr double kDropThreshold = -0.04;   // 落后 40ms 就丢帧
constexpr double kMaxDelay      =  0.20;   // 最多等 200ms
```

### 平滑化：帧长自适应

单纯 `diff > 0` 就 sleep，会让帧率抖动。更稳的做法参考 ffplay：

```cpp
double frame_duration = 1.0 / fps;                 // 平均帧长
double sync_threshold = max(frame_duration, 0.01); // 小于阈值视为"可忽略误差"

if (fabs(diff) < sync_threshold) {
    delay += diff;      // 微小偏差，通过微调显示时长吸收
} else if (diff < 0) {
    delay = 0;          // 落后明显，尽快追
}

> 注意：`delay` 是**墙钟等待秒数**，而帧间隔与偏差是内容秒。变速时必须 `delay /= speed`（2x 时帧间隔 0.033s 只等 0.0165s），否则变速下画面节奏永远追不上音频（docs/06 坑 AB）。
```

## 4. 变速播放

变速 = 把"显示时刻"按倍率拉伸：

- 视频：`frame_pts * speed` 与主时钟比较（或主时钟按 speed 缩放，本项目用后者：`PlaybackClock::set_rate`）；
- 音频：**必须重采样**。WASAPI 按固定 48kHz 输出，变速后播放器以 `48k ÷ speed` 的速率解码+重采样，用 libswresample 完成，否则音调会变（除非用 time-stretch 算法，那是后话）；
- 同步：变速只改时钟倍率，追帧算法不变。

## 5. Seek（跳转）

跳转是"时间复位 + 管线复位"的组合拳，顺序错了就会花屏或崩溃：

```cpp
void MediaPlayer::seek(double target) {
    // 1. 先停解码/消费：把包队列、帧队列全部 flush
    video_q_.flush();  audio_q_.flush();
    video_frames_.flush(); audio_frames_.flush();
    // 2. 解码器内部缓冲 flush（清掉 B 帧重排状态）
    video_decoder_->flush(); audio_decoder_->flush();
    // 3. 让解封装跳转（向后找最近关键帧）
    source_.seek(target);   // av_seek_frame(AVSEEK_FLAG_BACKWARD)
    // 4. 最后复位时钟：从 target 开始计
    sync_.seek(target);
}
```

为什么第 4 步要最后做？如果先复位时钟，管线在"新时间"上跑旧帧，会出现短暂画面跳变/音频错乱。

另外还有一步隐藏复位：`audio_.reset_stream()`（在复位时钟之前调用）。它把 WASAPI 设备缓冲里 seek 前的旧音频 Stop/Reset 掉，否则旧数据还会继续播 0.2s，主时钟却已跳到新位置，seek 后画面会比声音快一个固定值（docs/06 坑 AA）。

另两个与 seek 相关的坑（v0.2.10 修复）：
- **切换文件时音频计数未归零**：WASAPI 的已播帧计数（played_frames_）跨文件残留，新文件首帧对齐会出现 audio_offset=-219s 这类错误值；打开新文件前必须在释放音频对象时归零。
- **seek 后音频起播等待**：4K 中段 seek 找关键帧可能超过 500ms，超时后若继续用旧偏移的主时钟会卡顿/跳变。等待上限放宽到 1.5s，超时后回退单调时钟（从 seek 目标起算），新音频帧到达时重新锚定；进度条 seek 也改为主线程异步执行，避免 avformat_seek_file 阻塞渲染线程。

## 6. 缺失时间戳与异常

| 异常 | 处理 |
| --- | --- |
| `frame->pts == AV_NOPTS_VALUE` | 用上一帧 pts + 平均帧长递推，并记日志 |
| 帧 pts 突然倒退（seek 后残留） | 帧队列按 pts 单调性丢弃乱序帧 |
| 音频 EOF 但视频还有 | 主时钟冻结在最后位置，视频按原节奏播完 |
| 视频 EOF 音频还有 | 画面保持最后一帧，音频自然播完 |

## 反例：不用主时钟，按固定帧率播放

```cpp
render(frame); Sleep(1000/60);
```

后果：

- 音频没有"老板"，两路各走各的，几十秒后音画错位半秒起；
- 变帧率内容（部分 MKV、GIF）节奏全乱；
- 慢盘/网络抖动直接变成整体漂移，且无法自我修正。
