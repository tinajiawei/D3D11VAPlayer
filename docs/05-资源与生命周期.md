# 05 资源与生命周期

> 多线程 + 大量堆内存的项目里，崩溃通常不是"逻辑错"，而是"谁负责释放、线程怎么退出"没想清楚。本篇讲这两件事，并附上本项目踩过的真实坑。

## 1. 作用

回答三个问题：

1. FFmpeg 的对象（AVPacket/AVFrame/AVFormatContext...）由谁释放、怎么保证不漏？
2. 线程如何优雅退出，阻塞在队列里的线程怎么叫醒？
3. 出错时如何不崩、不静默、可排查？

## 2. RAII：把"忘了释放"从根上消灭

FFmpeg 的 C 接口要求每个 `av_*_alloc` 配一个 `av_*_free`。散落各处写配对代码，任何异常路径都会漏。

本项目做法（`src/core/av_utils.h`）：每个对象配一个删除器，包进 `unique_ptr`：

```cpp
struct AvPacketDeleter {
    void operator()(AVPacket* p) const { av_packet_free(&p); }
};
using AvPacketPtr = std::unique_ptr<AVPacket, AvPacketDeleter>;
```

之后代码里只有 `AvPacketPtr`，离开作用域自动释放，**删除配对问题从此不存在**。

### 常见误解：unique_ptr 包了就能随便搬？

不能。`AVPacket` 内部有引用计数的 buffer（`AVPacket.buf`），直接拷贝是浅拷贝，两个指针会争抢释放。所以：

- 转移所有权：`std::move`（本项目队列里全是 move）；
- 需要复制：显式 `av_packet_clone` / `av_frame_clone`（深拷贝）；
- 千万别把同一个 `AVPacket*` 存两份。

## 3. 帧内存所有权

解码器 `pop(AVFrame* out)` 的协议是 **move_ref**：解码器把帧的内容"搬"进调用者的 frame，自身变空。一条链路上所有权是清晰的：

```
解码线程 make_frame() → pop() 获得帧 → push 进 FrameQueue（move）
→ 渲染线程 pop_front() → draw_frame() 用完 → unique_ptr 自动释放
```

每一步只有一个持有者，没有"谁先释放"的争议。

## 4. 线程优雅退出（最容易写错的地方）

### 协议：abort + notify_all + join

```cpp
void close() {
    running_ = false;
    video_packets_.abort(); audio_packets_.abort(); video_frames_.abort();
    audio_.stop();                     // 停音频回调线程
    stop_threads();                    // 依次 join
    ...
}
```

三个必须：

1. **abort 在 join 之前**：先唤醒所有阻塞在队列上的线程，join 才不会死等；
2. **abort 内部必须 notify_all**：否则沉睡的 pop 永远醒不来（见 01 篇）；
3. **join 顺序按依赖反向**：解封装 → 解码 → 渲染。先杀消费者再杀生产者，避免"生产者还在往已关闭的队列塞"。

### 为什么不能用"强制杀线程"

Windows 的 `TerminateThread` 不会执行析构：锁可能永远不释放、堆可能损坏、FFmpeg 内部状态可能半更新。多线程程序只有一种退出方式——**通知 + 等待**。

## 5. 错误处理与容错

### 统一 Error 对象

所有模块返回 `Error{code, message}`，不抛异常、不返回裸错误码。好处：错误信息跟着错误码走，日志里直接能看懂。

### 三级容错策略

| 层级 | 例子 | 策略 |
| --- | --- | --- |
| 可恢复 | 音频设备不可用 | 降级静音，视频照播，只警告一次 |
| 可降级 | 硬解打开失败 | 自动回退软解（DecoderFactory 的职责） |
| 不可恢复 | 文件打不开、没有流 | 返回错误给 UI，不启动播放 |

### 项目里的真实容错点

- **无音频设备**：`IAudioClient::Initialize` 失败 → 不创建音频线程，`audio_done_` 直接置 true，结束判定不卡住；
- **解码失败**：记日志后按 EOF 处理，不让播放器挂死；
- **时间戳缺失**：`AV_NOPTS_VALUE` 用上一帧 + 帧长递推。

## 6. 踩坑实录（本项目真实修过的 bug）

### 坑 1：NULL 字符串指针 → ucrtbase 的 strlen 崩溃

**现象**：视频能播，音频一打开就崩，崩溃地址在 ucrtbase 的 strlen。

**根因**：音频解码器的 `ctx_->pix_fmt` 是 `AV_PIX_FMT_NONE(-1)`，`av_get_pix_fmt_name(-1)` 返回 **NULL**；日志宏把 NULL 直接丢给 `operator<<`，内部调 strlen(NULL)。

**教训**：C 风格字符串进日志/流之前必须判空。这个 bug 用 WER 报告 + dumpbin 反汇编定位，排查过程见 06 篇。

### 坑 2：环形缓冲 count 下溢

**现象**：并发测试永远跑不完。

**根因**：drop_oldest 分支里 `count_ -= drop` 时 drop 大于 count_，size_t 下溢成巨大值，后续读写全部错乱。

**教训**：无符号减法前先 `min(count_, overflow)`；这类 bug 单元测试必须覆盖"满+丢弃"路径。

### 坑 3：测试输出被管道缓冲吞掉

**现象**：测试挂起时什么都看不到。

**根因**：`Out-String` 缓存全部输出直到进程退出；挂起进程的输出永远不显示。

**教训**：诊断挂起程序时用文件重定向（stderr 无缓冲），别用管道聚合。

### 坑 4：默认音频端点失效被误判为"没有声卡"

**现象**：声卡明明在（设备管理器能看到、音频服务运行中），音频初始化却一直失败。

**根因**：默认端点是虚拟音频设备，对 `IAudioClient::Initialize` 报 `AUDCLNT_E_DEVICE_INVALIDATED (0x88890008)`；程序只打了一句"初始化失败"，被误读为无设备。

**教训**：错误码必须带 HRESULT；设备类资源要做"枚举全部端点 + 逐个尝试 + 失败重试"的容错（本项目实现在 `AudioOutput` 中）。完整排查过程见 06 篇第 8 节。
### 坑 5：有界队列的消费者忘记通知生产者（帧队列死锁）

**现象**：播放器只渲染队列深度（8 帧）后就定格，解码线程沉睡。

**根因**：`FrameQueue::pop_front` 没有 `notify_one`，生产者阻塞在"队列满"时永远等不到空间。

**教训**：条件变量配对的铁律——**任何改变等待条件状态的操作都必须 notify**。push 通知消费者，pop 也要通知生产者，flush/abort 通知所有人。已加回归测试（tests/test_frame_queue.cpp）。排查过程见 06 篇第 9 节坑 A。
